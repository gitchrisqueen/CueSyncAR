CueSync AR

An open-source iOS app that watches a real pool table through the camera and draws the predicted shot on the cloth.

In development · not on the App Store · build it yourself

View the code on GitHub How to build it

What it is

CueSync AR is an augmented-reality billiards coach for iPhone and iPad. You point the camera at a real table and mark its four corners. From then on the app detects the balls and the cue stick in the live camera feed, tracks them in a coordinate system locked to the table, and draws the aim line, the ghost ball, the post-impact paths and cushion rebounds onto the cloth in AR.

It is a personal open-source project, MIT licensed, developed in the open. There is no App Store listing, no TestFlight beta and no sign-up. The only way to run it today is to build it from source with Xcode and put it on your own device. If you do not write software, there is nothing here for you to install yet.

How it works

Three steps, and the app is honest about each one.

  1. 1

    Point

    Hold the phone or iPad so the whole table is in frame. The app runs an ARKit world-tracking session on the live camera feed. A physical device is required — the Simulator has no camera and shows a placeholder.

  2. 2

    Calibrate

    Tap the four corners of the playing surface, drag to fine-tune, then lock. That builds a table-space coordinate system rooted to an AR anchor on the real table, snapping to a standard table size when your corners land within 8 % of one. The measurement is saved along with ARKit's map of the room, so a table you have already set up can be recognised again on a later launch instead of re-measured.

  3. 3

    Aim

    A bundled Core ML detector finds balls and the cue stick in each frame; a tracker gives them stable identities in table space; a pure Swift solver works out the ghost ball, the post-impact paths and cushion rebounds. RealityKit draws the result anchored to the table. Aim comes from the cue stick when it is visible, and falls back to where the device is pointing when it is not. Tap a pocket to call a shot.

Where it actually stands

This section is deliberately unflattering. The project's rule is that a claim about accuracy carries a measured number and a link to the run that produced it, or it is not made — so most of the interesting numbers are simply absent below.

Built and running in the app

Implemented and wired in. How much of it has been checked at a real table is the next column.

  • Live AR camera feed and the four-corner calibration flow
  • Saved calibrations, restored by relocalizing the AR world map
  • On-device ball and cue-stick detection from a bundled Core ML model
  • Live aim, ghost ball, trajectory and cushion-rebound overlays
  • A coaching card with the cut angle and tip-offset guidance
  • Called shots: tap a pocket and the ring turns green when the prediction sends the ball in
  • Tap-to-designate the cue ball, for practice balls the detector cannot classify
  • A settings sheet, a session recorder, and a local-network debug mirror

Verified at a real table: one session

23 July 2026 · one iPad · one 8 ft table

  • Reopening a saved table — the app re-recognising the room and restoring the measurement — took 2 s on each of three consecutive relaunches. But the first attempt after saving a fresh map took 90–150 s, in the two observations recorded.
  • Anchor-rooted overlays stayed flat on the cloth after relocalization (before/after photos are committed with the run).
  • Stick-based aiming engaged with the cue on the table 86 % of the time, up from 50 %, after a hold-time fix.
  • A recorded negative result: running CPU-only, the on-device detector was blind to a ball moving at shot speed — only rest positions were recoverable. The detector has since been allowed onto the Neural Engine behind a crash-safe probe, but that has not been exercised at a table, so the result above is still the last one measured.

Not done, and not claimed

  • Overlay positions still sit a few centimetres off the real balls. Two causes have been found and fixed in code; neither fix has been confirmed at a table yet.
  • Predicted-versus-actual bank paths: one uncalibrated data point so far.
  • External-display (TV) output exists as a tested package but is not yet wired into the app. Projector output with geometric alignment is not built at all.
  • Guided drill content, a game-rules engine, spin and english physics: all planned, none built.
  • No performance, battery or thermal profiling. No App Store hardening. No release build of any kind.

How it is built

On-device machine learning
A fine-tuned YOLOv11n detector, exported to Core ML and bundled with the app, run through Vision. It scored mAP@50 of 0.896 on its own validation set at export — that is a measure of the model, not of the app's aiming accuracy, and the two should not be confused.
ARKit and RealityKit
World tracking, plane raycasting and world-map persistence from ARKit; overlays drawn as RealityKit entities rooted to AR anchors, so they stay put as ARKit refines its map.
Swift 6, SwiftUI, iOS 26
Swift 6 language mode with strict concurrency, a SwiftUI app lifecycle, and a minimum deployment target of iOS 26 on iPhone and iPad.
A thin app over pure packages
Eleven local Swift packages hold the real logic — physics, table geometry, perception, tracking, deterministic replay, UI. They import no ARKit and are tested on both Linux and macOS in CI, so most of the project can be worked on without a table or even a Mac.
No third-party runtime dependencies
No package manifest in the repository fetches a remote dependency. There is no analytics SDK, no crash reporter and no telemetry of any kind in the tree.
No account, ever
There is no sign-in and no user identity anywhere in the app, and the project runs no backend of its own. Session recordings are written to the app's own Documents folder on the device. The note below covers the two ways data can leave it.

Two things do touch the network — both are yours to control

The debug mirror is on by default in the current development build. When a session is running it serves the rendered screen and tracking JSON over your local network on port 8787, with no authentication, to anyone on the same LAN — and over that same port it will list and serve any session recordings held on the device. It exists so the device can be watched from a laptop while it sits at a table. Turn it off in Settings if you do not want it.

A hosted-detection adapter exists for comparing candidate models. It is only used if you deliberately pick a hosted model in the debug model picker and supply your own API key in an untracked local config file. No key ships with the repository. Left alone, detection runs entirely on the device.

Build it from source

You need macOS with Xcode 26 or newer, XcodeGen (brew install xcodegen), and a physical iPhone or iPad running iOS 26. The Xcode project is generated from project.yml and is not committed. 

git clone https://github.com/gitchrisqueen/CueSyncAR.git
cd CueSyncAR
Scripts/bootstrap.sh        # generates CueSyncAR.xcodeproj
open CueSyncAR.xcodeproj    # then build and run on a device

AR and the camera need real hardware. The package logic does not: on any machine with Swift 6.1 or newer, including Linux, this runs every package's test suite.
